# Git 提交规范指南

本指南详细说明如何编写规范的Git提交信息，遵循Conventional Commits规范。

## 提交信息格式

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### 格式要求

1. **标题行**：不超过 **50个字符**，使用祈使语气（"添加"而非"添加了"）
2. **空行**：标题与正文之间必须有一个空行
3. **正文**：每行不超过72个字符，解释**为什么**做这些更改（而非仅描述做了什么）
4. **Footer**：用于引用issue或标记破坏性变更

## 类型说明

| 类型 | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(UI): 添加用户登录功能` |
| `fix` | 修复bug | `fix(API): 修复数据接口超时问题` |
| `refactor` | 重构代码 | `refactor(Core): 重构数据处理逻辑` |
| `style` | 样式调整 | `style(UI): 优化按钮样式` |
| `docs` | 文档更新 | `docs: 更新README使用说明` |
| `test` | 添加测试 | `test(Core): 添加单元测试` |
| `chore` | 杂项/配置 | `chore: 更新项目规则配置` |
| `perf` | 性能优化 | `perf(DB): 优化查询性能` |

## 范围(Scope)建议

**⚠️ 注意：范围是完全可选的！** 简单项目或小型改动完全可以省略范围。

范围用于说明改动影响的模块，建议根据项目实际情况灵活定义：

### 定义原则

- **完全可选** - 简单改动可以省略，如：`git commit -m "docs: 更新README"`
- 使用**简短**的模块名（2-10个字符）
- 保持**一致性**，同一模块始终用相同名称
- 可以是**文件夹名**、**功能模块**或**组件名**

### 常见范围示例

```bash
# 按项目结构
feat(Views): 添加设置窗口
fix(Models): 修复待办项序列化问题
refactor(Services): 重构数据服务

# 按功能模块
feat(Parser): 优化智能解析
fix(Tray): 修复托盘图标问题
perf(Startup): 优化启动速度

# 按组件
feat(Widget): 添加透明度调节
style(Archive): 优化归档列表样式

# 范围可选，简单改动可以省略
docs: 更新README
chore: 更新依赖包
```

**建议：** 个人开发不必过于严格，选择**最直观**的模块名即可，关键是保持项目内一致性。

## 提交信息示例

### 新功能（带body说明）

```bash
feat(Widget): 添加窗口透明度记忆功能

保存用户设置的透明度到配置文件，并在启动时自动恢复。
这样可以避免用户每次启动都需要重新调整透明度。

Fixes #15
```

### 修复bug（简洁版）

```bash
fix(Tray): 修复托盘图标消失问题

修复在特定情况下托盘图标不显示的问题。
原因是系统主题切换时图标句柄失效。
```

### 重构

```bash
refactor(Parser): 重构智能解析逻辑

将解析逻辑拆分为多个小方法，提高可维护性。
便于后续添加新的解析规则。
```

### 破坏性变更（两种方式）

```bash
# 方式1：使用 ! 标记
feat(API)!: 修改配置存储格式

BREAKING CHANGE: 配置格式从XML改为JSON，
旧版本配置文件将不再兼容。

# 方式2：使用 BREAKING CHANGE footer
feat(API): 修改配置存储格式

BREAKING CHANGE: 配置格式从XML改为JSON，
旧版本配置文件将不再兼容。
```

### 简单改动（无body）

```bash
style(Archive): 优化归档Tab动画折叠效果
docs: 更新README使用说明
chore: 更新项目依赖包版本
```

## Footer 格式

```bash
# 关联Issue
Fixes #123
Closes #456
Related to #789

# 破坏性变更
BREAKING CHANGE: 描述破坏性变更的影响

# 签名（可选）
Signed-off-by: 用户名 <邮箱@example.com>
```

## 最佳实践

### 提交频率

- ✅ 完成一个独立功能点 → 立即提交
- ✅ 修复一个bug → 单独提交
- ✅ 重构代码 → 单独提交，便于回滚
- ❌ 避免一次性提交大量不相关更改
- ❌ 避免一个提交包含多个功能

### 提交信息原则

1. **标题简洁** - 不超过50个字符，使用祈使语气
2. **空行分隔** - 标题与正文之间必须有空行
3. **说明为什么** - 正文解释改动的理由和背景
4. **行宽限制** - 正文每行不超过72个字符
5. **关联问题** - 使用Footer引用issue：`Fixes #123`
6. **破坏性变更** - 用 `!` 标记或 `BREAKING CHANGE:` footer
